## 二、产品定位（不可动摇）

> **本产品不是彩票预测工具。**

**定位：** 「基于真实历史开奖数据的大乐透**娱乐分析**与**选号辅助**工具」。

所有页面和功能必须明确：
- 仅提供统计分析和娱乐参考；
- **不代表预测**；
- **不保证中奖**；
- 页面需保留风险提示/免责声明。

## 三、未来产品升级方向

> v2.0 阶段（历史走势图 / 多源数据 / 达人推荐 / 综合推荐 / 用户选号 / 首页仪表盘）的详细执行路线见独立文档 **`V2-ROADMAP.md`**；v2.0 启动前必须阅读该文档并重新评估数据结构/走势图数据层/多源采集层/用户交互模块。
> **V3 方向**：数据架构升级为 **Cloudflare D1 长期历史开奖数据库**（全量导入 + 每日增量，作为综合分析/评分/走势图/达人推荐的唯一基础数据源），详见 `V2-ROADMAP.md` 第十章，当前仅规划不开发。
> **V4 方向**：**用户体系**（当前保持游客访问模式）——未来建设用户注册管理系统（账号/收藏号码/历史分析记录/个性化偏好/方案管理），建立在历史数据库与分析模型稳定之后，不提前引入认证/数据库/权限复杂度，详见 `V2-ROADMAP.md` 第十一章。

### **单一最终推荐原则（Phase 9-C，2026-08-21）**

> **核心架构**：
> 1. **后台允许多模型并行**：热度模型、冷热模型、遗漏模型、趋势模型、结构模型、回测模型可同时运行
> 2. **所有模型只作为内部计算层**：禁止直接输出多个推荐方案给用户
> 3. **新增最终推荐层**：综合评分 + 权重融合 + 历史回测验证 → 生成唯一 final_recommendation
> 4. **前端产品原则**：普通用户页面只能展示一个最终推荐号码组合
> 5. **推荐更新机制**：开奖完成后重新分析 → 生成下一期唯一推荐 → 更新前端
> 
> **产品理由**：
> - 普通用户只需要一个明确的「下一期 AI 综合推荐」号码
> - 避免多个推荐方案造成选择困难
> - 符合「娱乐分析、选号辅助」的产品定位
> 
> **状态**：✅ 已固化并生效

### 第一阶段：v1.3 产品体验升级

- **目标**：从「数据展示页面」升级为「用户体验产品」。
- **重点**：首页第一视觉展示最新开奖结果。
- **首页顺序**：
  品牌介绍 → 最新开奖结果 → 数据覆盖（1000期真实数据）→ 下一期娱乐分析推荐 → 数据统计 → 历史报告 → 免责声明
- **最新开奖展示要素**：期号 / 开奖日期 / 前区 5 个号码 / 后区 2 个号码 / 更新时间 / 数据来源
- **状态**：✅ 本阶段已实施上线（v1.3 基线）

### 第二阶段：v1.4 选号助手模块

- **目标**：让用户从「查看分析」变成「使用工具」。
- 功能：
  1. **机选推荐**：随机生成大乐透号码，支持单注 / 多注生成；
  2. **手动选号**：用户点击号码选择——前区 1-35 选 5 个、后区 1-12 选 2 个，生成自己的号码；
  3. **智能补全**：用户选择部分号码后，依据 1000 期历史统计、热冷趋势、奇偶比例、大小比例，提供娱乐补全；
  4. **选号分析**：用户输入号码后，分析历史出现频率、热冷情况、遗漏情况、奇偶比例、大小比例、和值。

### 第三阶段：v1.5 数据可视化升级

- **1000期走势图**：
  - 前区走势图：35 个号码长期变化；
  - 后区走势图：12 个号码长期变化；
  - 展示：出现轨迹、遗漏周期、热度变化。
- **冷热趋势图 / 号码频率图 / 遗漏趋势图**。

### 第四阶段：v2.0 数据体系升级

- **目标**：提升数据可信度——多数据源校验。
- **架构**：官方开奖数据 + 500彩票网 + 其他公开来源 → 统一验证层。
- **原则**：不是为了增加来源数量，而是**数据一致性验证**（以官方数据为权威基准）。

### 第五阶段：v2.x 达人推荐融合

- 采集全网公开达人推荐数据（公众号、网站、视频平台公开推荐）→ 形成「达人推荐号码池」。
- 分析：号码出现次数、市场关注热度、推荐共识指数。
- **注意**：不是认为达人预测准确，只是作为**娱乐分析维度**。

### 第六阶段：AI 综合娱乐分析

- 综合：1000期历史数据 + 走势图 + 冷热趋势 + 遗漏分析 + 达人推荐热度。
- 生成：多维娱乐分析报告，例如——解释为什么选择这些号码，展示统计依据。

## 四、开发原则（每次开发必须遵守）

1. 优先用户体验；
2. 不轻易增加复杂后台；
3. 不为了功能数量而功能堆积；
4. 先上线可见成果，再优化；
5. 小步迭代；
6. 保持现有稳定架构；
7. 修改前先只读检查；
8. 前端展示优化优先于后台重构。
